# Dive C: ML personalization and few-shot cloning of an individual, across domains

Date: 2026-09-11. Scope: voice cloning, in-context imitation, per-user adapters and hypernetworks, LLM personalization, DreamBooth-style small-data personalization, behavioural-cloning evaluation, and blending a population prior with one person's evidence. The question each time is what carries over to "user's games in, clone engine out".

Method: I checked every title below against the page-1 text using pymupdf. Every quote and number was found in the extracted PDF text; the extracted text sits next to each PDF as `lit/pdf/<id>.txt`. Where I could not find a number, the table says so and quotes none. No local computation was run beyond PDF text extraction.

## Answers to the five search questions

1. **Would reading a user's games as a prompt beat fitting a code?** Probably not for us. VALL-E needed 60K hours from many speakers. Prompt-DT works because its tasks differ in one factor visible within 2 to 15 timesteps. USER-LLM (#7) finds a learned encoder beats raw history in the prompt. Chess identity is weak per game, so a prompt-reading model needs a very large and diverse player pool and gives no clear gain over a code. What does carry over is the **amortized encoder** (#6, #7): games → code or LoRA in one pass, used to initialize or replace gradient fitting.
2. **Per-user adapters versus one embedding at small data.** With a frozen shared base, per-user LoRA beats prompting/retrieval (#4). A hypernetwork matches per-user LoRA at every history length (#6). Assembling a user from a shared bank matches their own LoRA (#5). An embedding into a fixed head "can be limiting" (#8). No paper found a single embedding beating per-user adapters. Diversity of training users is the stated bottleneck (#6).
3. **Small-data generative personalization.** Embedding-only (textual inversion) is safe but saturates, and more data barely helps (#10). Weight fine-tuning captures more detail but drifts, so it needs a prior-preservation loss (#9) or an L2/KL anchor to the base (#11).
4. **Per-step accuracy versus whole-trajectory fidelity.** Theory: errors compound as T²ϵ (#14). Empirically, offline error "weakly correlated" with rollout quality (#15). Humans can judge human-likeness reliably (0.77 to 0.84 accuracy). Automated classifiers match humans only on coarse questions, not fine ranking (#16).
5. **Population prior plus individual evidence.** Standard options are model interpolation, data interpolation or clustering, with the weight set by the user's sample size (#12, #11). For retrieval or cache mixtures, set the weight per query from match quality (#13).

## Top 5 ML ideas for user-games → clone-engine (ranked)

1. **Anchored low-rank fine-tune (DreamBooth prior preservation + Ditto λ).** Add a rank-4 to rank-8 LoRA on the upper blocks and train it on the user's games. The loss has two extra terms: (a) KL to the frozen base on held-out population positions at the user's rating (prior preservation), and (b) an L2 anchor with λ scaled by 1/games. Go beyond the 512-d code, since it is embedding-only and saturates (#8, #10).
   - Expected: middlegame +0.5 to 1.5 pp for users with 1k to 5k games. This is extrapolated from the ~10k-game full fine-tune result, not measured. Never worse than base at 50 games.
   - Data/compute: 50 to 5,000 games. On CPU, about 10 to 30 minutes for 5k games at 19.5M params (estimate).
   - CPU feasible: yes.
   - Risk: medium. The gain may stay opening-only.
2. **Amortized clone encoder (P2P/USER-LLM style).** Train a games → code (later LoRA) encoder on as many *distinct* players as possible (the Lichess 1k to 2.8k pool). Use it for instant clones and as the starting point for idea 1.
   - Expected: matches the fitted code's +4 to 5 pp instantly. A more diverse pool may lift the stranger-retention figure (88 to 96%).
   - Data/compute: one GPU training run. Per user, one CPU forward pass.
   - Risk: medium. A 120-player head is too narrow (#6: diversity over quantity).
3. **Match-dependent book/cache weight (adaptive kNN-LM).** Replace the fixed Dirichlet strength with a weight based on how many times the user has seen this exact position, and extend to near-duplicate positions from the user's own games.
   - Expected: +0.3 to 1 pp beyond the exact-book +3.6 pp, mostly in early middlegame transpositions.
   - Data/compute: none new. CPU trivial.
   - Risk: low.
4. **Rollout-based and human-judge evaluation as the main score.** Compare clone self-play against the player's real game statistics per game phase, looking for systematic biases. Run a small human pairwise Turing test with about 30 judges × 10 pairs. Use automated judges only for the coarse "bot or human" question.
   - Expected: no accuracy gain, but it prevents choosing the wrong clone (#14 to #16).
   - Compute: CPU self-play.
   - Risk: low. Cost is human time.
5. **Build users from a shared adapter bank (Per-Pcs / 2502.14998).** Give each user a sparse mixture of K shared low-rank adapters, fit on CPU as roughly 10 to 50 mixture weights. Borrow idiosyncrasies from similar players (clustering, #12).
   - Expected: between the code and idea 1. It may help 50 to 500-game users the most.
   - Compute: GPU once to build the bank. CPU per user.
   - Risk: medium to high. Welch 2022 found similar-user gains small.

## 3 most decision-changing facts

1. **Embedding-only personalization saturates, and prior-anchored weight updates are the known fix.** Textual inversion: more data gives "paltry improvement in reconstruction". Low-rank-plus-sparse: a user embedding into a fixed model "can be limiting". DreamBooth and Ditto keep weight fine-tuning safe at small data. Our flat middlegame (≤0.4 pp) is the expected ceiling of a code, not a sign that the middlegame is impersonal.
2. **Per-step accuracy is a weak proxy for how the clone plays.** Errors compound as T²ϵ, the bound is tight, and driving models with identical offline error "differ dramatically". Automated human-likeness judges fail at fine-grained ranking (NTT), which matches our 3 failed judge-reward attempts. A small human test is feasible: 30 judges reach 0.77 to 0.84 accuracy.
3. **Amortized per-user weights match per-user training, but only with diverse training users.** P2P outperforms OPPU and is 33x faster at deployment, and "training user diversity is more critical than sheer quantity". Scale the number of distinct players before building anything more elaborate. Prompting with raw games is not the route (VALL-E needed 60K hours; USER-LLM's encoder beats the raw-history prompt).
